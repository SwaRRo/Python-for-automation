Chapter 11 · Build-along

Capstone: build one complete feature

Bring the concepts together in a small task tracker. You can later swap the data domain for products, stock movements, bookings, or another business workflow.

Estimated time: 1–3 practice sessionsRead, type, explain, practice

Purpose: finish one useful vertical slice

This capstone turns the previous ten chapters into one small, traceable feature: a task tracker that lists saved tasks, creates a task, and marks a task complete. The feature is deliberately ordinary. The same path later fits a product, booking, stock movement, or note, but a small task gives us enough data, validation, persistence, and failure cases to practise the whole system.

By the end, you can…

  • Write a record and API contract before asking for code.
  • Follow one click from React state to a backend write and back to the screen.
  • Provide loading, empty, success, validation, and failure states.
  • Test the important behaviour, audit AI output, and make one safe iteration.

A vertical slice means one user-visible outcome works across every layer. “The button renders” is not a slice. “A user enters Send invoice, the server validates it, SQLite stores it, and the task is still present after restart” is.

1. Vocabulary and the mental model

Think of the app as a chain of responsibilities, not as one magical program.

UI
React components, form controls, and state. It gathers input and displays a state; it does not open SQLite.
API contract
The agreed request and response shapes, including error meanings. It is the handshake between frontend and backend.
Backend
FastAPI code that validates input, applies business rules, and calls storage. It is trusted to make the final decision.
Persistence
SQLite data that remains after the process stops. A Python sqlite3 call or Rust database code owns this operation.
Sidecar
A separate executable, such as a packaged FastAPI service, started and supervised by Tauri. It has lifecycle and permission work.
State
Data the UI must remember while it runs: tasks, the current title, a loading flag, and an error message.

One architecture fact to keep straight

React runs in a webview. It does not query SQLite directly. You choose either a direct Tauri/Rust command (Rust performs the database operation) or a FastAPI sidecar (Tauri starts a separate local service, and the UI uses HTTP). These are distinct choices. A sidecar adds process startup, shutdown, loopback networking, packaging, and permission decisions; direct commands reduce that process management but require more Rust integration. Keep the same API-like contract either way.

2. Write the contract before writing the screen

Start with nouns and transitions. Our Task has a SQLite-assigned integer id, a trimmed title containing 1–120 characters, a Boolean done that starts false, and a backend-assigned UTC ISO-8601 created_at timestamp. The client sends only the title when creating a task. The server assigns the ID and timestamp; this prevents a browser from pretending that a record already exists.

Pseudocode · the promise of the featureTask: id, title, done, created_at
POST /tasks with {"title": "Prepare report"} → 201 + saved Task
GET /tasks → bare Task[] JSON array
PATCH /tasks/{id} with {"done": true} → 200 + saved Task
DELETE /tasks/{id} → 204, no response body
Unknown id → 404; invalid input → 422
UI states: loading | empty | ready | saving | error

Notice the contract says what happens on failure. It also says where each value comes from. The UI may reject an empty title early for a friendly message, but the backend repeats the rule because a request can come from any client, not only our React form.

3. Worked example: trace “Add task” end to end

Step 1: make a boring, honest UI

Build the static shape first: a labelled input, an Add button, a list, and a status region. Reuse the TaskScreen from Chapter 07. In browser development, it calls the same-origin /api/tasks path; Vite strips /api and forwards to FastAPI’s /tasks route as configured in Chapter 05. In React, keep title, tasks, isLoading, isSaving, and error in state; compute filtered lists rather than storing duplicate values.

JSX · the essential form behaviour<form onSubmit={handleSubmit}>
  <label htmlFor="task-title">Task title</label>
  <input
    id="task-title"
    value={title}
    onChange={(event) => setTitle(event.target.value)}
    maxLength={120}
    disabled={isSaving}
  />
  <button type="submit" disabled={isSaving}>
    {isSaving ? "Saving…" : "Add task"}
  </button>
</form>

value makes the input controlled by React. onChange copies the latest browser value into state. maxLength gives immediate feedback, while the backend still validates. Disabling the button during the request prevents an accidental double-click from creating two rows; the server should still consider a duplicate request policy if duplicates matter to the domain.

Step 2: make the request and interpret the response

The handler trims whitespace, rejects a blank title, turns on the saving state, and uses the browser’s fetch. An HTTP response can be a failure even when fetch itself resolves, so check response.ok. Only after parsing a successful response do we append the returned record. That returned record is authoritative because the backend selected its ID and timestamp.

JavaScript · readable request flowasync function handleSubmit(event) {
  event.preventDefault();
  const cleanTitle = title.trim();
  if (!cleanTitle) {
    setError("Enter a task title.");
    return;
  }

  setIsSaving(true);
  setError("");
  try {
    const response = await fetch("/api/tasks", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ title: cleanTitle })
    });
    if (!response.ok) throw new Error("The server rejected the task.");
    const savedTask = await response.json();
    setTasks((current) => [...current, savedTask]);
    setTitle("");
  } catch (requestError) {
    setError("Could not save the task. Check that the service is running and try again.");
  } finally {
    setIsSaving(false);
  }
}

finally is important: it turns the button back on after both success and failure. Do not display the raw exception to a user; log diagnostic details during development, but give the UI a safe, actionable message.

Step 3: load with visible states

On initial load, set isLoading before requesting GET /tasks. Render “Loading tasks…” while waiting, “No tasks yet” for a successful empty array, and a retryable error after a network or HTTP failure. These are different states, not decorative wording: the user needs to know whether to wait, add the first item, or retry.

Mark a task done only after the API confirms it

In the list, use the database ID as the React key and send a narrow completion update. Replace the row with the returned server record only after response.ok; on failure, leave the old value visible and show an error.

JavaScript · completion request inside TaskScreenasync function markDone(task) {
  setIsSaving(true);
  setMessage("");
  try {
    const saved = await requestJson(`/api/tasks/${task.id}`, {
      method: "PATCH",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ done: !task.done }),
    });
    setTasks((current) => current.map((item) =>
      item.id === saved.id ? saved : item
    ));
  } catch (error) {
    setMessage(error instanceof Error ? error.message : "Update failed.");
  } finally {
    setIsSaving(false);
  }
}

The shared requestJson helper from Chapter 07 checks response.ok and parses the returned Task. There is no optimistic change to roll back: the checkbox or button reflects saved server state, including after a reload.

4. Let FastAPI validate and SQLite persist

On the FastAPI side, a request model describes the incoming JSON. The endpoint trims and checks the title, then uses a parameterized SQL statement. The question mark is not a placeholder to fill by string concatenation; it is a bound value. That keeps data separate from SQL text and avoids injection mistakes.

Python · a compact FastAPI/SQLite shapeimport os
import sqlite3
from contextlib import closing
from datetime import datetime, timezone
from pathlib import Path

from fastapi import FastAPI, HTTPException, Response
from pydantic import BaseModel, Field, StrictBool, field_validator

class TaskCreate(BaseModel):
    title: str = Field(min_length=1, max_length=120)

    @field_validator("title", mode="before")
    @classmethod
    def trim_title(cls, value):
        return value.strip() if isinstance(value, str) else value

class TaskDoneUpdate(BaseModel):
    done: StrictBool

class TaskRead(BaseModel):
    id: int
    title: str
    done: bool
    created_at: str

def create_app(db_path: Path) -> FastAPI:
    db_path = Path(db_path)
    db_path.parent.mkdir(parents=True, exist_ok=True)
    app = FastAPI(title="Task MVP")

    def connect():
        connection = sqlite3.connect(db_path)
        connection.row_factory = sqlite3.Row
        return connection

    def initialize_database():
        with closing(connect()) as connection:
            with connection:
                connection.execute("""
                    CREATE TABLE IF NOT EXISTS tasks (
                        id INTEGER PRIMARY KEY,
                        title TEXT NOT NULL CHECK(length(title) BETWEEN 1 AND 120),
                        done INTEGER NOT NULL DEFAULT 0 CHECK(done IN (0, 1)),
                        created_at TEXT NOT NULL
                    )
                """)

    def as_task(row):
        return {
            "id": row["id"],
            "title": row["title"],
            "done": bool(row["done"]),
            "created_at": row["created_at"],
        }

    initialize_database()

    @app.get("/tasks", response_model=list[TaskRead])
    def list_tasks():
        with closing(connect()) as connection:
            rows = connection.execute(
                "SELECT id, title, done, created_at FROM tasks ORDER BY id"
            ).fetchall()
        return [as_task(row) for row in rows]  # bare JSON array

    @app.post("/tasks", response_model=TaskRead, status_code=201)
    def create_task(item: TaskCreate):
        title = item.title.strip()
        if not title or len(title) > 120:
            raise HTTPException(status_code=422, detail="Title must be 1–120 non-space characters")
        created_at = datetime.now(timezone.utc).isoformat(timespec="seconds").replace("+00:00", "Z")
        with closing(connect()) as connection:
            with connection:
                cursor = connection.execute(
                    "INSERT INTO tasks (title, done, created_at) VALUES (?, ?, ?)",
                    (title, 0, created_at),
                )
                row = connection.execute(
                    "SELECT id, title, done, created_at FROM tasks WHERE id = ?",
                    (cursor.lastrowid,),
                ).fetchone()
        return as_task(row)

    @app.patch("/tasks/{task_id}", response_model=TaskRead)
    def update_task(task_id: int, item: TaskDoneUpdate):
        with closing(connect()) as connection:
            with connection:
                cursor = connection.execute(
                    "UPDATE tasks SET done = ? WHERE id = ?",
                    (int(item.done), task_id),
                )
                if cursor.rowcount == 0:
                    raise HTTPException(status_code=404, detail="Task not found")
                row = connection.execute(
                    "SELECT id, title, done, created_at FROM tasks WHERE id = ?",
                    (task_id,),
                ).fetchone()
        return as_task(row)

    @app.delete("/tasks/{task_id}", status_code=204)
    def delete_task(task_id: int):
        with closing(connect()) as connection:
            with connection:
                cursor = connection.execute("DELETE FROM tasks WHERE id = ?", (task_id,))
                if cursor.rowcount == 0:
                    raise HTTPException(status_code=404, detail="Task not found")
        return Response(status_code=204)

    return app

DATA_DIR = Path(os.environ.get("APP_DATA_DIR", "./dev-data")).expanduser().resolve()
app = create_app(DATA_DIR / "tasks.sqlite3")

The nested with connection: commits a successful transaction or rolls it back when an exception escapes; it does not close the connection. The outer closing(connect()) guarantees closure. lastrowid gives the database ID, then the second query reads back the complete saved row. Every SQL value uses a ? placeholder; the title never becomes part of SQL text.

The example creates a SQLite file under APP_DATA_DIR. In local development it defaults to ./dev-data; for a packaged sidecar, the Tauri host must set this variable to the operating system’s per-user application-data directory. SQLite stores booleans as integers, so the API converts them to JSON booleans. The UI never needs to know that storage detail.

Transfer to the app: a stock movement would add a quantity and reason, and the backend would check the business rule before inserting. The React form is not allowed to decide whether inventory may go negative; that is a trusted backend rule.

5. Choose the desktop boundary deliberately

During development, the React webview can call a local FastAPI service on loopback. In a packaged desktop app, Tauri must start and stop that service, bundle a compatible executable, restrict its arguments and permissions, and handle a port or process failure. This is the sidecar architecture. It is useful when you already have Python code or want the API boundary to remain clear, but it is not automatic.

The direct-command architecture replaces the HTTP call with a narrow Tauri command. Rust validates the command arguments or calls a Rust SQLite layer, then returns a serializable task. It avoids a second process and loopback server, but you must learn the Rust command boundary, capabilities, and database integration. In both choices, keep the same record contract and user-facing states. Do not make React import a SQLite driver.

For this course, finish the feature with the FastAPI path you learned in Chapters 8–9, then write down the direct-command alternative as a deliberate later iteration. If you package the sidecar, test startup when the port is unavailable, shutdown when the window closes, and the permissions that allow only the intended binary and arguments.

6. Test behaviour, then audit the generated code

Tests are executable examples of the contract. Start with the backend because it is easier to test without a browser. FastAPI’s official testing pattern uses TestClient and ordinary Python assert statements.

Python · contract and persistence testfrom fastapi.testclient import TestClient
from main import create_app

def test_create_complete_and_reload_task(tmp_path):
    db_path = tmp_path / "test-tasks.sqlite3"

    with TestClient(create_app(db_path)) as client:
        invalid = client.post("/tasks", json={"title": "   "})
        assert invalid.status_code == 422

        created = client.post("/tasks", json={"title": "Send invoice"})
        assert created.status_code == 201
        task = created.json()
        assert task["title"] == "Send invoice"
        assert task["done"] is False
        assert task["created_at"].endswith("Z")

        boundary = client.post("/tasks", json={"title": " " + "x" * 120 + " "})
        assert boundary.status_code == 201
        assert boundary.json()["title"] == "x" * 120
        assert client.delete(f"/tasks/{boundary.json()['id']}").status_code == 204

        coerced_boolean = client.patch(f"/tasks/{task['id']}", json={"done": 1})
        assert coerced_boolean.status_code == 422
        updated = client.patch(f"/tasks/{task['id']}", json={"done": True})
        assert updated.status_code == 200
        assert updated.json()["done"] is True

    # A fresh app object using the same file simulates a process restart.
    with TestClient(create_app(db_path)) as restarted:
        tasks = restarted.get("/tasks").json()
        assert tasks == [updated.json()]
        missing = restarted.patch("/tasks/999999", json={"done": True})
        assert missing.status_code == 404

        deleted = restarted.delete(f"/tasks/{task['id']}")
        assert deleted.status_code == 204
        assert restarted.get("/tasks").json() == []

tmp_path gives the test a fresh database file, and the second TestClient proves the record survives constructing a new app with the same file. Then exercise the UI: first load, empty list, successful create, blank title, server stopped, double-click, unknown ID, and restart. A screenshot alone cannot prove that the saved data is durable.

AI audit checklist

Ask AI for a bounded review, not an entire ERP. Give it the contract and ask it to explain assumptions. Read every suggested line and compare it with this checklist:

  1. Does every field keep the same name and type from form to JSON to database to response?
  2. Is validation repeated at the trusted boundary?
  3. Are SQL values bound with parameters rather than string formatting?
  4. Can loading and saving flags get stuck after an exception?
  5. Does the UI update only after the server confirms success?
  6. What happens if the service is offline, the ID is missing, or the user retries?

Make one small iteration from the audit. For example, if generated code keeps a local optimistic task before the database responds, replace it with the returned saved task. Commit that change and record why it is safer. AI can suggest code, but your contract, tests, and explanation are the acceptance criteria.

Common mistake → symptom → fix

  • React calls SQLite directly → import or permission errors, or an unsafe desktop boundary → fix: call a narrow Tauri command or HTTP endpoint; let the privileged layer access storage.
  • Only the UI validates → another client stores blank or overlong titles → fix: validate again in FastAPI/Rust and return a clear status.
  • Ignore response.ok → a 422 response is treated like a saved task → fix: branch on HTTP status before updating state.
  • Forget finally → one network error leaves “Saving…” forever → fix: reset loading flags in one guaranteed cleanup path.
  • Use SQL string formatting → quotes break a title and untrusted input can alter a query → fix: use ? parameters.
  • Package a sidecar without lifecycle tests → the desktop app works on the developer’s machine but cannot find or stop its backend → fix: document startup, loopback binding, target binaries, permissions, and shutdown behaviour.

Beginner exercise: design before you code

As a stretch exercise, change the task feature into a “daily note” feature. Write a new contract with fields id, title, body, archived, and created_at. Specify the create request, one update operation, at least three invalid or failed cases, and the exact UI state shown for loading and failure. Then identify which layer owns each rule. This is a separate design; do not add note fields to the Task API without updating every layer.

Show a worked answer and explanation 
Contract · one possible answerNote: id integer, title 1–80 chars, body 0–2000 chars,
      archived boolean, created_at timestamp

POST /notes with {title, body}
  trim title; reject blank/overlong title or overlong body
  insert archived=false; return saved Note

PATCH /notes/{id} with {archived: boolean}
  return 404 when id is not present

UI states:
  loading: “Loading notes…”
  empty: “No notes yet.”
  failure: “Notes could not be loaded. Retry.”
  success: render the server-returned note

The answer is strong because it names boundaries. The input control can show character counts, but FastAPI or a direct Tauri command makes the final decision. SQLite stores the record and transaction; React owns temporary input and visible state. The same tests from the task example now become note tests: blank title returns 422, creation returns a server ID, and archiving an unknown ID returns 404.

Definition of done

Development vertical slice: the React/Vite screen loads a bare Task array, creates a task, marks it done, shows loading/empty/error states, FastAPI returns the documented status codes, SQLite persists the server-assigned ID and UTC timestamp, and the test proves data survives a new app instance. “The button looks right” is not enough. Packaged desktop tier: separately choose direct Rust commands or a bundled FastAPI sidecar, set the OS application-data path, and verify process startup/shutdown, loopback/origin policy, sidecar permissions, and target-specific binaries. The course’s Vite proxy disappears from a packaged app, so do not call the development slice a finished installer.

Recap and next-step bridge

You began with pseudocode, froze one Task contract, reused a React screen that updates only from server-confirmed data, validated at FastAPI, used parameterized SQLite writes with explicit connection closing, and tested create/complete/reload behaviour. You also made the important architecture distinction: a Tauri shell is not automatically a Python server, and React never becomes the database layer.

Next, turn this slice into your own domain one field at a time. Keep the first change small, write the new invariant before coding, and run the same audit after each iteration. When you are ready to package, study the Tauri sidecar permissions and target-binary rules—or implement one narrow Rust command—then test the desktop lifecycle rather than assuming development mode predicts release behaviour.
