Chapter 01 · Start here

Map the app before writing code

Learn the moving parts of a desktop application and trace a single piece of data through the interface, backend, and storage. This map will make every later chapter easier to place.

Estimated time: 25–40 minRead, type, explain, practice

Purpose: draw the route before you build the road

A desktop app is not one big program. It is a set of parts that cooperate across boundaries. Before writing buttons or database queries, you should be able to point at each part and explain its job. In this course, our running example is a small task list: a person types Prepare monthly report, saves it, and later sees it in a list.

By the end, you can…

  • Separate the interface, application rules, data access, and persistence layers.
  • Trace one task from a form to SQLite and back to the rendered list.
  • Explain the two valid desktop choices: a Tauri/Rust command or a separate FastAPI sidecar.
  • Describe what changes between development on your computer and a packaged app.

A vocabulary and mental model

Think of the app as a workshop with four stations. The presentation layer shows fields, buttons, and lists. Application logic checks rules such as “a task needs a title.” Data access translates a request into a database operation. Persistence is where the record remains after the app closes.

HTML
Structure for headings, forms, buttons, and lists.
CSS
Rules for appearance and layout; it does not save data.
JavaScript
Code in the webview that responds to events and moves data.
React
A JavaScript library for composing interface components and rendering from state.
FastAPI
A Python web framework that exposes typed HTTP endpoints.
SQLite
A relational SQL engine that normally stores tables in a local database file.
Tauri
A desktop shell that hosts a webview and connects it to native code.
Rust command
A trusted Tauri function that the frontend can invoke through Tauri’s message boundary.
Sidecar
A separate executable bundled with or launched by the desktop app, such as a Python API server.

One important boundary is easy to miss: React does not query SQLite directly. React runs in a webview. A trusted Rust command or a local API receives a request, validates it, and performs the privileged database work. This boundary makes responsibilities visible and prevents the interface from having unrestricted access to files.

Worked example: follow one task all the way through

Use this sequence whenever a feature feels confusing. We will follow the value Prepare monthly report as it changes shape.

  1. Input and UI state. The user types into an HTML input. React keeps the current text in a JavaScript string so the screen and the program agree about what is being edited.
  2. Save event. Clicking the button calls a function. The function trims accidental spaces and refuses an empty title before crossing the boundary.
  3. Request contract. The frontend sends a small object with a known field name. A contract is an agreement about names, types, and what comes back.
JavaScript · frontend shapeconst draft = { title: "Prepare monthly report" };

async function saveTask() {
  const title = draft.title.trim();
  if (!title) return;
  const saved = await sendTask({ title });
  showTask(saved);
}

const draft is an object with one string property. trim() removes leading and trailing whitespace. The early return stops an invalid save. await means the function pauses until the boundary returns; it does not pretend that disk or network work is instantaneous. The names title and saved make the direction of the data readable.

  1. Choose one trusted boundary. In a direct Tauri design, sendTask invokes a Rust command. In a FastAPI design, it makes an HTTP POST request to a local service. These are distinct choices, not two automatic layers.
  2. Validate and write. The receiving side checks the title, runs the application rule, and asks SQLite to insert a row. SQLite assigns an ID, which lets the app refer to this task later.
Python · create request modelfrom pydantic import BaseModel, Field

class TaskCreate(BaseModel):
    title: str = Field(min_length=1, max_length=120)

TaskCreate describes only client-owned input. FastAPI parses and validates that JSON before route logic runs. The backend—not the form—generates the ID and timestamp when it saves the record. The complete endpoint appears in Chapter 08; do not treat this request model as a complete route.

SQL · parameterized insertINSERT INTO tasks (title, done)
VALUES (?, ?);
-- Bound values supplied separately by sqlite3: (title, 0)

The question marks are placeholders: Python sends the SQL text and values such as (title, 0) separately. That makes a title containing an apostrophe ordinary data, not executable SQL. The data-access layer owns the table and parameter details so the UI does not need to know them.

  1. Return and render. The response travels back as an object such as {"id": 7, "title": "Prepare monthly report", "done": false, "created_at": "2026-10-06T08:30:00Z"}. React adds it to its list state, then renders a row. The user sees the result because the screen is derived from current state, not because React opened the database file.

The whole route is:

Data flowtyped title
  → React form state
  → save handler
  → Rust command OR FastAPI POST
  → validation and application rules
  → SQLite INSERT
  → saved record response
  → React list state
  → rendered task row

Why label every arrow?

Every arrow is a possible failure point or shape change: a string becomes JSON, JSON becomes a Python model, and a row becomes a response object. Naming the boundary tells you where to validate and test.

The course-wide Task contract

To make the later chapters fit together, we will keep one small record shape from JavaScript through Python and SQLite. When an example shows only the fields a screen needs, it is a view projection; it is not a different saved record.

Shared contract · fields and APITask = {
  id: integer chosen by SQLite,
  title: trimmed string, 1–120 characters,
  done: boolean, initially false,
  created_at: UTC ISO-8601 string chosen by the backend
}

POST /tasks   request {"title": "Prepare report"}  → 201 + saved Task
GET  /tasks   response Task[] (a bare JSON array)
PATCH /tasks/{id} request {"done": true}            → 200 + saved Task
DELETE /tasks/{id}                                  → 204, no body

Unknown id → 404     Invalid input → 422

The database assigns the ID; the backend owns the timestamp. The client sends only the title when creating and sends a Boolean when marking a task done. A 422 means the request data or business rule is invalid; a 404 means the requested record does not exist. The same names and shapes appear again in Chapters 03, 05, 07, 08, 09, and 11.

Development architecture versus packaged architecture

During development, you may run the frontend dev server, Tauri, and FastAPI in separate terminals. This is convenient for errors and quick restarts, but do not assume those processes will magically exist for a user.

Choice A: Tauri/Rust commands

The React frontend invokes a Tauri command. Rust validates the arguments and can use a SQLite library or a Tauri database plugin. When packaged, the command is compiled into the app, so there is no Python server to start. This can reduce lifecycle work and keep the local boundary inside the desktop process. You still need careful permissions, error handling, migrations, and tests.

Choice B: FastAPI as a sidecar

The Tauri host launches a separately packaged Python executable, and the frontend talks to its loopback HTTP address. The sidecar must be built for each target platform, started at the right time, stopped when the app closes, and restricted to safe arguments and local networking. This choice preserves Python code and can be useful when your rules already belong in Python, but it adds process, port, packaging, and security decisions.

In both choices, the webview is the presentation client. In neither choice does Tauri automatically host FastAPI, nor does putting files beside the app automatically make them a database API.

Development: What process, port, or command is running, and where are errors visible?
Packaging: What ships, who starts it, where is the database, and how are permissions and shutdown handled?

Common mistakes: symptom, cause, fix

  • Mistake: “React writes to tasks.db.” Symptom: the design asks browser code to open a local file or SQLite library directly. Fix: route the operation through a Rust command or FastAPI endpoint and validate at that boundary.
  • Mistake: treating FastAPI as part of Tauri by default. Symptom: the development app works only while a manually started terminal is open. Fix: either choose direct Rust commands or explicitly plan a sidecar’s binary, lifecycle, loopback address, and permissions.
  • Mistake: changing field names between layers. Symptom: the UI sends taskTitle but the backend expects title, so validation fails or a blank row appears. Fix: write one tiny contract and reuse its names in the form, request model, SQL mapping, and response.
  • Mistake: showing success before persistence finishes. Symptom: a task appears, then disappears after reload. Fix: wait for the save response, handle errors, and update the list with the returned record.

Beginner exercise: draw and explain the map

On paper or in a text file, draw boxes for React UI, one boundary, validation/application rules, and SQLite. Draw arrows for both “load tasks” and “save task.” Choose either a Rust command or FastAPI sidecar, then answer: where does the task title first become JSON, where is it checked, and what value returns to the UI?

Show a worked answer and explanation

Direct command: React state → Tauri invoke("create_task", { title }) → Rust validates and writes SQLite → task object → React list. Sidecar: React state → HTTP POST /tasks JSON → FastAPI validates → Python writes SQLite → JSON response → React list.

The important part is not drawing identical boxes. It is naming the owner of each job and identifying the return value, such as id: 7. If your diagram has React opening the database, redraw that arrow through a trusted boundary.

Recap and your next step

You now have a map: interface state starts a request; a trusted boundary validates it; application logic asks a data-access layer to write SQLite; a response returns an identified record; React renders from state. Tauri/Rust commands and FastAPI sidecars can both implement the boundary, but their process lifecycle and packaging costs differ.

Next, Chapter 02 zooms into the browser. You will build the form and list with HTML and CSS before adding JavaScript. Keep these arrows beside you: every feature should remain a journey from screen to storage and back.
