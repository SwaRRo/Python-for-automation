Chapter 04 · Foundations

Decisions, functions, and useful array methods

Programs make choices, reuse named operations, and transform lists. These ideas show up in every React application, from a checklist to a desktop ERP.

Estimated time: 40–55 minRead, type, explain, practice

Purpose: make small, explainable decisions

Chapter 03 introduced JavaScript values, objects, and arrays. Now we make those values do useful work. A program reads data, checks a rule, chooses a branch, and returns a result. Functions give those rules names; map, filter, and find help us work with lists without changing the original list by accident.

By the end, you can…

  • Write readable if/else decisions with strict comparisons.
  • Define and call functions and arrow functions with parameters and return values.
  • Choose map, filter, or find by the job you need to do.
  • Encode a capacity rule, report expected input problems, and handle unexpected failures safely.

Vocabulary and the mental model

Think of a function as a small, named machine. A parameter is the named input in its definition; an argument is the actual value supplied when you call it. A return value is the machine’s answer. Calling a function does not happen when you define it—you must write its name followed by parentheses.

A condition is an expression that becomes true or false. In an if statement, JavaScript runs the first block whose condition is true. Use === and !== for comparisons so a number such as 5 is not silently treated as the string "5". Use && for “and”, || for “or”, and ! for “not”.

The three array methods have three different questions:

  • map: “What new value should I make for every item?” It returns a new array with the same length.
  • filter: “Which items pass this test?” It returns a new array that may be shorter, including an empty array.
  • find: “What is the first item that matches?” It returns one item or undefined when there is no match.

Business rule versus screen detail

A rule such as “a reservation must be positive and no greater than available stock” is application logic. Put it in a small function that can be tested and reused. The trusted server or Tauri command must check it again before changing stored data; the architecture choices are mapped in Chapters 01 and 10.

Worked example: protect a stock reservation

Imagine the app has a small stock list. A user enters an item ID and quantity. The function should reject bad quantities, report a missing item, refuse a request over capacity, and accept a valid request. It returns a predictable object instead of making the screen guess what happened.

JavaScriptconst stock = [
  { id: "paper", name: "Printer paper", available: 8 },
  { id: "pens", name: "Blue pens", available: 20 }
];

function reserve(stock, itemId, quantity) {
  if (!Number.isInteger(quantity) || quantity <= 0) {
    return { ok: false, message: "Quantity must be a positive whole number." };
  }

  const item = stock.find((record) => record.id === itemId);
  if (item === undefined) {
    return { ok: false, message: "That item was not found." };
  }

  if (quantity > item.available) {
    return { ok: false, message: `Only ${item.available} are available.` };
  }

  return { ok: true, itemId: item.id, quantity };
}

const result = reserve(stock, "paper", 5);
console.log(result); // { ok: true, itemId: "paper", quantity: 5 }

Follow the data one step at a time

  1. stock is an array of two objects. Each object has an ID, a display name, and a capacity number.
  2. reserve receives three arguments. Inside the function, they are available through the parameters stock, itemId, and quantity.
  3. The first if uses Number.isInteger and a comparison. A decimal, zero, negative number, or non-number exits early with an error-shaped result.
  4. find tests each record until record.id === itemId. For "paper", it returns the paper object. The explicit undefined check handles a missing ID before we try to read available.
  5. The capacity branch compares the requested quantity with the record’s current availability. A request for 9 is rejected; a request for 5 continues.
  6. The final object has ok: true, so a caller can display success without parsing a sentence. Every earlier branch has ok: false and a human-readable message.

The arrow function passed to find is a callback: find calls it once per record. Because its body is one expression, the expression is returned implicitly. The longer equivalent is function (record) { return record.id === itemId; }.

Ordinary and arrow functions

Use a function declaration when a named operation deserves a clear explanation. Use an arrow function often for a short callback or when assigning a small function to a variable. Both can accept parameters and return results.

JavaScriptfunction labelForTask(done) {
  if (done === true) {
    return "Done";
  }
  return "Open";
}

const labelForTaskShort = (done) => done ? "Done" : "Open";

const firstOpenTask = tasks.find((task) => task.done === false);

The first function uses an explicit return in each branch. The arrow version uses a conditional expression: choose the value after ? when true, otherwise the value after :. Do not shorten a rule so much that a beginner cannot tell what it means.

Common mistake: braces without a return

Symptom: tasks.map((task) => { task.title }) produces an array of undefined. Fix: parentheses mean an implicit return—tasks.map((task) => (task.title))—or write return task.title; inside the braces. Curly braces start a function body; they do not automatically return its last line.

Transform, select, and locate lists

Suppose we use the Chapter 01 Task data. These three records show only id, title, and done because this calculation does not need the timestamp; the stored Task still includes created_at.

JavaScriptconst tasks = [
  { id: 1, title: "Count stock", done: true },
  { id: 2, title: "Review order", done: false },
  { id: 3, title: "Print label", done: false }
];

const openTasks = tasks.filter((task) => task.done === false);
const titles = openTasks.map((task) => task.title);
const selected = tasks.find((task) => task.id === 2);

console.log(openTasks.length); // 2
console.log(titles);           // ["Review order", "Print label"]
console.log(selected.title);   // "Review order"

filter keeps complete task objects, so later code can still use their IDs. map then changes each remaining object into a title string. find stops at the first matching ID. These methods return new arrays or a found value; they do not remove records from tasks.

In the future React chapter, this same data flow can produce a list of elements:

JSX in a React componentconst visibleTasks = tasks.filter((task) => task.done === false);

return (
  <ul>
    {visibleTasks.map((task) => (
      <li key={task.id}>{task.title}</li>
    ))}
  </ul>
);

The stable database or locally generated id is the React key. Do not usually use the array index: when an item is inserted or removed, the index can point to a different record.

Expected problems and unexpected errors

Not every rejected reservation is a crashed program. Invalid quantity, missing item, and insufficient capacity are expected business outcomes; return a result the UI can explain. A network, parsing, or programmer failure is different. At a boundary such as a later API call, use try/catch to keep the screen from failing silently and to show a safe message.

JavaScripttry {
  const result = reserve(stock, "paper", 12);
  if (result.ok === false) {
    console.log(result.message); // expected business feedback
  }
} catch (error) {
  console.error(error);          // diagnostic detail for development
  console.log("Could not complete the reservation.");
}

Do not use catch to hide every bug or show raw error details to a user. Validate at the UI for a quick response, but repeat important validation at the trusted backend or Tauri/Rust command before changing stored data. The next chapter will add asynchronous requests and JSON, where transport failures become a real concern.

Common mistakes: symptom → fix

  • = in a condition → a value changes unexpectedly or the branch behaves strangely. Use === for comparison.
  • Reading a missing find result → “Cannot read properties of undefined.” Check item === undefined before reading a property.
  • Using map to select items → the array keeps its length and may contain undefined. Use filter first.
  • Using an unstable list key → the wrong row appears to keep focus or state after a reorder. Use a stable unique ID.
  • Mutating the source array while “transforming” → another part of the screen sees surprising data. Prefer the new arrays returned by these methods.

Beginner exercise

Write openTitles(tasks). It must return the titles of unfinished tasks, in their original order. Then call it with the tasks array above. Add one rule: if there are no unfinished tasks, return an empty array. Explain why the operation that selects records is different from the operation that changes their shape.

Show the worked answer and explanation 
JavaScriptfunction openTitles(tasks) {
  const openTasks = tasks.filter((task) => task.done === false);
  return openTasks.map((task) => task.title);
}

const result = openTitles(tasks);
console.log(result); // ["Review order", "Print label"]

filter answers “which task objects should remain?” and therefore produces zero or more task objects. map answers “what value should I take from each remaining object?” If every task is done, filter produces [], and map also produces []—no special branch is needed.

Recap and the next bridge

Readable application logic follows a visible path: validate inputs, locate the relevant record, apply the business rule, and return a result. if/else chooses a branch. Functions package one job and make parameters and return values explicit. filter selects many, map transforms every selected item, and find locates one. Expected rule failures can be returned; unexpected failures can be caught at a boundary and reported safely.

In Chapter 05, the same functions will wait for data from HTTP. You will learn promises, async/await, and JSON while keeping this chapter’s discipline: inspect the value’s shape, check failure paths, and keep UI code separate from the service and database.
