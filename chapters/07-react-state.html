Chapter 07 · Core skill

React state, forms, and data-driven screens

State is the information a component remembers. When you update state with its setter, React renders again so the screen reflects the new information.

Estimated time: 45–65 minRead, type, explain, practice

Purpose: make a screen remember and respond

A static React component can display a task list, but a useful app must remember what the person is typing, which task is selected, and whether a request is still running. This chapter connects the JavaScript data and async ideas from Chapters 03–05 to the React components from Chapter 06. You will build a small, honest task screen: the form is controlled by React, the list is rendered from records, and every request has a visible loading, error, success, or empty state.

By the end, you can…

  • Explain why useState is different from an ordinary local variable.
  • Update objects and arrays by replacing them instead of mutating them.
  • Connect a controlled form to validation and an async save.
  • Render lists with stable record IDs and handle all meaningful request states.

Vocabulary and a useful mental model

State
Data a component remembers between renders, such as a draft title or a list of tasks.
Setter
The function returned by useState. Calling it asks React to remember a new value and render again.
Controlled input
A form field whose current value comes from React state and whose onChange updates that state.
Immutable update
A replacement update: create a new array or object rather than changing the old one in place.
Key
A stable identity for one item among its siblings. A database ID is usually the right key.

Think of rendering as a photograph. React takes the current state, calculates the JSX picture, and puts that picture in the browser. An ordinary variable is redrawn from scratch on the next render, so it cannot be the component’s memory. State supplies both memory and a signal to take a new photograph.

jsximport { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

useState(0) gives the initial number. Array destructuring names the number count and its setter setCount. The click handler does not edit the button directly; it requests a new value. React renders again, and {count} then displays that value.

Worked example: a task screen, one decision at a time

Use the shared Task contract from Chapter 01: the server supplies a stable integer id, trimmed title, done boolean, and created_at timestamp. The create request sends only title. Updating the screen from server-returned records prevents a temporary browser ID from being mistaken for a saved database ID.

jsximport { useEffect, useState } from "react";

const TASKS_URL = "/api/tasks";

async function requestJson(url, options) {
  const response = await fetch(url, options);
  const body = response.status === 204
    ? null
    : await response.json().catch(() => null);

  if (!response.ok) {
    const detail = typeof body?.detail === "string"
      ? body.detail
      : `Request failed (${response.status})`;
    throw new Error(detail);
  }
  return body;
}

export default function TaskScreen() {
  const [tasks, setTasks] = useState([]);
  const [title, setTitle] = useState("");
  const [status, setStatus] = useState("loading");
  const [message, setMessage] = useState("");
  const [isSaving, setIsSaving] = useState(false);
  const [reloadNumber, setReloadNumber] = useState(0);

  useEffect(() => {
    let ignoreResult = false;
    async function loadTasks() {
      setStatus("loading");
      try {
        const records = await requestJson(TASKS_URL);
        if (!Array.isArray(records)) throw new Error("The API did not return a task list.");
        if (!ignoreResult) {
          setTasks(records);
          setStatus("ready");
          setMessage("");
        }
      } catch (error) {
        if (!ignoreResult) {
          setMessage(error instanceof Error ? error.message : "The list could not load.");
          setStatus("error");
        }
      }
    }
    void loadTasks();
    return () => { ignoreResult = true; };
  }, [reloadNumber]);

  async function handleSubmit(event) {
    event.preventDefault();
    const cleanTitle = title.trim();
    if (!cleanTitle || cleanTitle.length > 120) {
      setMessage("Enter a task title from 1 to 120 characters.");
      return;
    }

    setIsSaving(true);
    setMessage("");
    try {
      const saved = await requestJson(TASKS_URL, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ title: cleanTitle }),
      });
      if (!saved || typeof saved.id !== "number") throw new Error("The API did not return a saved Task.");
      setTasks((current) => [...current, saved]);
      setTitle("");
      setMessage("Task saved.");
      setStatus("ready");
    } catch (error) {
      setMessage(error instanceof Error ? error.message : "The task could not be saved.");
    } finally {
      setIsSaving(false);
    }
  }

  async function toggleDone(task) {
    setIsSaving(true);
    setMessage("");
    try {
      const saved = await requestJson(`${TASKS_URL}/${task.id}`, {
        method: "PATCH",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ done: !task.done }),
      });
      if (!saved || typeof saved.id !== "number") throw new Error("The API did not return the updated Task.");
      setTasks((current) => current.map((item) => item.id === saved.id ? saved : item));
    } catch (error) {
      setMessage(error instanceof Error ? error.message : "The task could not be updated.");
    } finally {
      setIsSaving(false);
    }
  }

  if (status === "loading") return <p role="status">Loading tasks…</p>;
  if (status === "error") {
    return (
      <section>
        <p role="alert">{message}</p>
        <button type="button" onClick={() => setReloadNumber((n) => n + 1)}>Try again</button>
      </section>
    );
  }

  return (
    <section>
      <form onSubmit={handleSubmit}>
        <label htmlFor="task-title">Task title</label>
        <input id="task-title" value={title} maxLength={120}
          onChange={(event) => setTitle(event.target.value)} disabled={isSaving} />
        <button type="submit" disabled={isSaving}>{isSaving ? "Saving…" : "Add task"}</button>
      </form>
      {message && <p role="status">{message}</p>}
      {tasks.length === 0 ? <p>No tasks yet. Add the first one.</p> : (
        <ul>
          {tasks.map((task) => (
            <li key={task.id}>
              <button type="button" disabled={isSaving} onClick={() => toggleDone(task)}>
                {task.done ? "Mark open" : "Mark done"}
              </button>
              <span>{task.title}</span>
              <time dateTime={task.created_at}>{task.created_at}</time>
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}

Follow the data flow

  1. Initial render: tasks is an empty array, title is an empty string, and status is "loading". The early return tells the user what is happening instead of showing a misleading empty list.
  2. Loading: useEffect runs after the first render and again whenever reloadNumber changes, so the retry button can request the list again. It asks the HTTP endpoint for JSON. It does not talk to SQLite: React calls an API boundary, while FastAPI or a Tauri/Rust command owns the data operation.
  3. Success or error: A non-2xx response is treated as failure. On success, the response array becomes state and status becomes "ready". On failure, the message becomes visible through an alert.
  4. Typing: The input displays title. Every change event reads event.target.value synchronously and stores it with setTitle. React is now the source of truth for the draft.
  5. Submitting: preventDefault() stops a full-page navigation. Trimming and the length check give immediate feedback. The handler sends only { title } to POST /api/tasks, then adds the full server-returned Task—including its database ID and timestamp—only after success.
  6. Updating a record: map creates a new array. Only the matching task gets a new object via {...task}; every other task is returned unchanged. The new boolean is derived from the old one.
  7. Rendering: map turns each record into one list item. key={task.id} lets React match that task even if another task is inserted, removed, or reordered.

State is a view of saved data

This worked example waits for the API before changing a persisted record in React state. The browser calls the development-only /api proxy described in Chapter 05; FastAPI owns validation and SQLite writes. React does not query SQLite directly. A packaged app must choose a real Tauri/Rust command or a managed FastAPI sidecar as explained in Chapter 10.

Immutable updates: replace, do not secretly edit

Methods such as push, pop, splice, and direct assignment change an existing array. In state, prefer operations that return replacements:

  • Add: setTasks(current => [...current, newTask]).
  • Remove: setTasks(current => current.filter(task => task.id !== taskId)).
  • Update one object: setTasks(current => current.map(task => task.id === taskId ? {...task, done: true} : task)).

The functional form, current =>, is useful when the next value depends on the previous one. It prevents a quick series of events from calculating against an outdated variable. For nested objects, copy each level that changes; do not mutate a nested property through the old reference.

Loading, error, success, and empty are different facts

A blank list can mean “still loading,” “the server failed,” or “there are no records.” Those are different experiences and need different UI. A small status state such as "loading", "ready", and "error" prevents contradictory messages. When saving, add a separate saving boolean if necessary so the submit button can be disabled and duplicate requests avoided.

For an effect that depends on a changing ID, protect against an older response arriving late. A cleanup flag can ignore a result that is no longer relevant. In a larger app, a data-fetching cache may be preferable; the important beginner lesson is that network uncertainty must be represented rather than hidden.

Common mistake → symptom → fix

  • Mutating with tasks.push(newTask) → the list may not update, or another component sees surprising data. Fix: use a setter with [...current, newTask].
  • Using key={index} → after deleting or reordering, the wrong row can keep focus or local state. Fix: use a stable ID from the record; never generate a new key during rendering.
  • Using value={title} without onChange → the field is read-only. Fix: update state from event.target.value, or intentionally use defaultValue for an uncontrolled field.
  • Showing “No tasks” while loading → users think their records disappeared. Fix: check loading and error before the empty condition.
  • Calling a successful local update “saved” → data vanishes after restart. Fix: only report persistence after the backend or Rust command confirms it.

Beginner exercise

Add a “Delete” button to the worked task list. It should remove only the clicked task, refuse a blank title, and show “No tasks yet” when the last task is gone. Before reading the answer, say aloud which value changes, which new array is created, and where the stable key comes from.

Show the worked answer and explanation 
jsxasync function deleteTask(taskId) {
  setIsSaving(true);
  setMessage("");
  try {
    await requestJson(`${TASKS_URL}/${taskId}`, { method: "DELETE" });
    setTasks((current) => current.filter((task) => task.id !== taskId));
    setMessage("Task deleted.");
  } catch (error) {
    setMessage(error instanceof Error ? error.message : "The task could not be deleted.");
  } finally {
    setIsSaving(false);
  }
}

// Inside the task map:
<button type="button" disabled={isSaving} onClick={() => deleteTask(task.id)}>
  Delete
</button>

The click passes the record’s stable ID, not its position. The worked answer first waits for the API’s 204 No Content; only then does filter make a replacement array without that record. If the request fails, the row remains visible so the screen does not claim a deletion that never happened.

Recap and next-step bridge

State is component memory plus a re-render request. Controlled inputs make the draft explicit. Immutable array and object updates give React clear replacement values. Stable keys preserve each record’s identity. A data-driven screen is not complete until it distinguishes loading, error, success, and empty outcomes. Finally, React state is a view model, not a database: persistence belongs behind an intentional Tauri/Rust or FastAPI boundary.

In Chapter 08, you will refresh Python and build FastAPI endpoints that validate the task shape. Bring this chapter’s flow with you: form input becomes a request, the backend validates it, and the response becomes trustworthy UI state.
