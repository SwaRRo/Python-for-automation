Chapter 02 · Foundations

HTML, CSS, and the browser

Before React, learn the browser’s basic materials: semantic markup, forms, and styles. React will still use these same browser elements.

Estimated time: 35–50 minRead, type, explain, practice

Purpose: build a screen the browser can understand

HTML, CSS, and the browser are the first layer of the app. HTML gives a task screen meaning and order. CSS controls its spacing and layout. The browser (or a desktop webview) parses both and turns them into pixels and interactive controls. React, which arrives in Chapter 06, does not replace these foundations; it creates the same kinds of elements from JavaScript.

By the end of this lesson, you should be able to:

  • Choose semantic elements such as <main>, <form>, <label>, and <button> for their meaning.
  • Explain how a label is connected to an input and why native controls help keyboard and assistive-technology users.
  • Use the CSS box model, Grid or Flexbox, and a media query to keep a task screen usable at different widths.
  • Describe the path from source HTML and CSS to a browser/webview screen, without confusing the UI with the API or database.

Vocabulary and the browser mental model

Element
A piece of HTML with a role, such as a heading, form, input, or list item.
Semantic
Meaningful to people and tools. A <button> says “activate an action”; a generic <div> says nothing by itself.
Selector
The part of a CSS rule that chooses which elements receive styles, such as .task-form.
Box model
The layers around an element: content, padding, border, and margin.
Viewport
The visible area in a browser window or webview. Its width changes when the window or device changes.

Think of a page as a small pipeline. The browser reads HTML into a document tree. It reads CSS into style rules, matches those rules to the tree, calculates each box’s size and position, and paints the result. A click or key press creates an event. Native controls already know useful behavior; JavaScript can listen and add application behavior later.

Source order is a usability feature

Write content in the order it should be read: page heading, form, then task list. CSS can place columns side by side, but a screen reader, keyboard user, and narrow screen still benefit from a sensible HTML order. Use ARIA only when native HTML cannot express the meaning; do not use it to disguise the wrong element.

Worked example: a semantic task form

Start with structure before decoration. This example is a static version of the “create task” screen from the course architecture.

HTML<main>
  <h1>Tasks</h1>
  <form class="task-form">
    <label for="task-title">Task title</label>
    <input id="task-title" name="title" type="text" required>

    <label for="task-priority">Priority</label>
    <select id="task-priority" name="priority">
      <option value="normal">Normal</option>
      <option value="high">High</option>
    </select>

    <button type="submit">Save task</button>
  </form>
  <section aria-labelledby="task-list-heading">
    <h2 id="task-list-heading">Current tasks</h2>
    <ul>
      <li>Review weekly stock report — High</li>
      <li>Email supplier — Normal</li>
    </ul>
  </section>
</main>

Read the data flow line by line. <main> identifies the page’s primary content, and <h1> names the screen. The form groups controls that will eventually be submitted. The label’s for value exactly matches the input’s id; clicking “Task title” therefore focuses the input, and assistive technology can announce its name. The name values describe the keys a submission would carry. required lets the browser reject an empty title before application code runs.

The select gives a finite choice instead of asking the user to type a value with unknown spelling. The explicit type="submit" documents the button’s job. The list uses <ul> and <li> because these are repeated items, not a collection of unrelated boxes. aria-labelledby connects the section to its visible heading; in many cases the native heading and section structure are already enough, so add attributes deliberately.

Style the structure, not each individual element

CSS* {
  box-sizing: border-box;
}

.task-form {
  display: grid;
  gap: 0.75rem;
  max-width: 34rem;
}

.task-form input,
.task-form select,
.task-form button {
  min-height: 2.75rem;
  padding: 0.6rem 0.7rem;
}

@media (max-width: 40rem) {
  .task-form button {
    width: 100%;
  }
}

The universal rule makes declared widths include padding and borders, which avoids many surprising overflows. Grid gives the form one vertical track and a consistent gap. The grouped selector gives the three controls a comfortable touch target without repeating the same declarations. The maximum width keeps lines and controls readable on a large screen. The media query changes only when the viewport is narrow; it makes the primary action easy to tap without pretending that every phone has the same pixel width.

Layout, responsiveness, and accessibility in practice

Use Grid when you are arranging rows and columns, and Flexbox when you are aligning items along one direction, such as a toolbar. Prefer flexible units such as rem, percentages, minmax(), and max-width over a fixed canvas. Test by narrowing the window until content would otherwise become cramped; that content failure is a better breakpoint than a device-name guess.

Accessibility is not a separate polish phase. Keep visible labels, a logical heading order, sufficient color contrast, and a visible keyboard focus indicator. A link navigates to a location; a button performs an action. Do not turn a clickable <div> into a fake button: it will not reliably receive focus or respond to the expected keys. Do not use placeholder text as the only label because it disappears while typing. Browser validation is helpful feedback, but a future API must validate again because users can bypass a browser UI.

Inspect, do not guess.

In browser Developer Tools, inspect an element to see its DOM, matched CSS rules, computed box dimensions, and event-related messages. The “responsive” device toolbar is useful for testing width, but keyboard testing with Tab and Enter/Space is equally important.

Connection to the course app: screen versus storage

In this chapter, the form is only a screen. A user enters a title, the browser represents that value in an input control, and a submit event can later be handled by JavaScript. Chapter 03 teaches the JavaScript object that could represent the record, and Chapters 05 and 08 explain sending a request and validating it.

Keep the boundaries clear. React renders the interface inside a browser or Tauri webview; React does not query SQLite directly. One possible later path is UI → FastAPI sidecar → SQLite. FastAPI would be a separate local process with startup, shutdown, loopback networking, and packaging decisions. Another path is UI → Tauri command → Rust code → SQLite, with Tauri owning the privileged desktop operation. These are distinct choices with different lifecycle and security tradeoffs. This HTML lesson teaches the UI contract without assuming either backend exists.

Common mistake → symptom → fix

  • Generic clickable element → no keyboard focus or activation → use a native <button> for an action and style it with CSS.
  • Label and input IDs do not match → clicking the label does nothing and the field has a weak accessible name → make for="task-title" and id="task-title" identical.
  • Fixed width plus padding → a control spills beyond the viewport → use box-sizing: border-box, flexible widths, and a tested breakpoint.
  • CSS selector is too specific → a small change breaks an unrelated rule → prefer a reusable class and inspect the cascade before adding more selectors.

Beginner exercise

Build a static “New task” screen. Include a page heading, a labeled title input, a labeled priority select with “Normal” and “High,” a submit button, and a list with two tasks. Add a CSS class that uses Grid, keeps the form under 34rem, and makes the button full width below 40rem. Then use only the keyboard to reach and submit the form.

Before checking the answer, say what each element means and predict what happens if the title is empty.

Worked answer and explanation

A correct answer uses the HTML pattern above, changing the heading to “New task” if that is your screen name. The input must have a visible label, matching for/id, a useful name, and required. The button is type="submit", not a styled paragraph. The two task rows belong in a list. The CSS needs display: grid, a gap, a readable max-width, and a narrow-viewport rule. With an empty required input, the browser blocks the submission and reports that the field needs a value; that is client-side feedback, not database storage. If your keyboard focus disappears, check that you did not remove the outline without providing a visible replacement.

Recap and next-step bridge

HTML supplies meaning and native behavior. CSS selects boxes, applies the cascade, and lays them out responsively. The browser parses, styles, lays out, paints, and dispatches events; a Tauri webview follows the same UI model inside a desktop window. Accessible forms use real controls, explicit labels, logical source order, and clear focus. The task screen can collect a value, but it does not decide where that value is persisted.

Next, Chapter 03 turns the form’s values into JavaScript data: strings, objects, and arrays. You will learn to describe one task as data before you make the screen dynamic.
