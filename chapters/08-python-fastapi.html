Chapter 08 · Backend foundation

Python refresh and FastAPI endpoints

You already know some Python. Reuse that knowledge to build a small HTTP API: functions receive validated input, apply rules, call data-access code, and return a response.

Estimated time: 50–70 minRead, type, explain, practice

Purpose and objectives

Chapter 7 showed how a React form holds state and waits for an HTTP response. Now we will build the Python side of that conversation. You will follow one task record from JSON at the request boundary, through validation and business rules, to a response that the screen can safely render.

By the end, you can:

  • Define separate Pydantic models for data coming in and going out.
  • Explain what FastAPI validates automatically and what your service must still decide.
  • Sketch readable CRUD endpoints with a service/repository boundary.
  • Choose useful status codes and return errors without leaking implementation details.

Vocabulary and a mental model ¶

An endpoint is a Python function reached by an HTTP method and path, such as POST /tasks. An API contract is the agreed shape of its request, response, and errors. CRUD names the four common operations: create, read, update, and delete.

A request model describes what the client may send. A response model describes what the server promises to send back. Pydantic turns type declarations into runtime checks, while FastAPI uses models to parse JSON and document the endpoint.

Keep the layers in order

Think of the flow as React form → HTTP/JSON → FastAPI endpoint → service rule → repository/data store → response model → React state. The endpoint translates HTTP concerns. The service decides application rules. The repository later translates those decisions into SQLite operations in Chapter 9. Do not put database code in React.

Step 1: describe the data boundary ¶

Suppose our app follows the shared contract from Chapter 01. The create request contains only a title; the server supplies the ID, initial done value, and timestamp. A narrow completion request contains a Boolean. The read model describes the full record that comes back:

Python · models.pyfrom pydantic import BaseModel, Field, StrictBool, field_validator

class TaskCreate(BaseModel):
    title: str = Field(min_length=1, max_length=120)

    @field_validator("title", mode="before")
    @classmethod
    def trim_title(cls, value):
        return value.strip() if isinstance(value, str) else value

class TaskDoneUpdate(BaseModel):
    done: StrictBool

class TaskRead(BaseModel):
    id: int
    title: str
    done: bool
    created_at: str

BaseModel gives each class Pydantic’s parsing and validation behavior. The annotation title: str says the value is text. The field_validator trims the incoming string first; then Field enforces a 1–120-character limit on the trimmed title. Thus 120 meaningful characters with surrounding spaces are accepted, while blank and overlong trimmed titles are rejected. The backend still repeats its business-rule check before writing.

TaskDoneUpdate uses StrictBool, so JSON must contain true or false; values such as 1, 0, "true", and null are not silently coerced. The read model includes the generated ID and timestamp, which the client cannot choose. This narrow endpoint avoids confusing “field omitted” with “field explicitly set to null”; add more editable fields only when the contract and storage change together.

If a request sends a title with the wrong type or too many characters after trimming, Pydantic checks it before the endpoint runs and returns a validation response, normally HTTP 422. A whitespace-only string becomes empty in the validator and fails the minimum length. Treat model validation as a boundary, not as permission to skip business rules.

Step 2: separate endpoint, service, and storage ¶

Start with an in-memory repository so the data flow is visible. It is a teaching stand-in: restarting the process loses records. Later, the repository methods can issue SQLite statements without forcing the endpoint to know SQL.

Python · app/repository.pyclass TaskRepository:
    def __init__(self):
        self.records: dict[int, dict] = {}
        self.next_id = 1

    def create(self, title: str) -> dict:
        from datetime import datetime, timezone
        task = {
            "id": self.next_id,
            "title": title,
            "done": False,
            "created_at": datetime.now(timezone.utc).isoformat(timespec="seconds").replace("+00:00", "Z"),
        }
        self.records[self.next_id] = task
        self.next_id += 1
        return task

    def list_all(self) -> list[dict]:
        return [self.records[key] for key in sorted(self.records)]

    def get(self, task_id: int) -> dict | None:
        return self.records.get(task_id)

    def set_done(self, task_id: int, done: bool) -> dict | None:
        task = self.records.get(task_id)
        if task is None:
            return None
        task["done"] = done
        return task

    def delete(self, task_id: int) -> bool:
        return self.records.pop(task_id, None) is not None

The dictionary is keyed by integer ID, so lookup is straightforward. create assigns a new ID and timestamp; get returns a record or None; set_done changes the Boolean; and delete reports whether a row existed. This repository is intentionally in memory, so it resets whenever the Python process restarts. Chapter 09 replaces it with SQLite without changing the HTTP contract.

Now put a small service in front of it. A service is where rules belong—for example, rejecting a title that is only whitespace. This rule is different from checking that the value is a string:

Python · app/service.pyfrom .models import TaskCreate
from .repository import TaskRepository

class TaskService:
    def __init__(self, repository: TaskRepository):
        self.repository = repository

    def create_task(self, item: TaskCreate) -> dict:
        clean_title = item.title.strip()
        if not clean_title or len(clean_title) > 120:
            raise ValueError("title must contain 1–120 non-space characters")
        return self.repository.create(clean_title)

    def list_tasks(self) -> list[dict]:
        return self.repository.list_all()

    def get_task(self, task_id: int) -> dict | None:
        return self.repository.get(task_id)

    def set_task_done(self, task_id: int, done: bool) -> dict | None:
        return self.repository.set_done(task_id, done)

    def delete_task(self, task_id: int) -> bool:
        return self.repository.delete(task_id)

service = TaskService(TaskRepository())

__init__ receives a repository instead of creating one inside every method. That is dependency injection in a beginner-sized form: a test can provide a fresh repository. The service owns trimming and the 1–120-character business rule. Its ValueError is translated to HTTP 422 at the route boundary; unknown IDs stay a separate result so the route can return 404.

Step 3: expose a CRUD contract ¶

These routes connect HTTP to the service. The decorators declare the method and path; the parameters tell FastAPI where values come from. The response model filters and documents the output:

Python · app/routes.pyfrom fastapi import APIRouter, HTTPException, Response
from .models import TaskCreate, TaskDoneUpdate, TaskRead
from .service import service

router = APIRouter()

@router.get("/tasks", response_model=list[TaskRead])
def list_tasks():
    return service.list_tasks()  # bare JSON array

@router.get("/tasks/{task_id}", response_model=TaskRead)
def read_task(task_id: int):
    task = service.get_task(task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    return task

@router.post("/tasks", response_model=TaskRead, status_code=201)
def create_task(item: TaskCreate):
    try:
        return service.create_task(item)
    except ValueError as error:
        raise HTTPException(status_code=422, detail=str(error)) from error

@router.patch("/tasks/{task_id}", response_model=TaskRead)
def mark_task_done(task_id: int, item: TaskDoneUpdate):
    task = service.set_task_done(task_id, item.done)
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    return task

@router.delete("/tasks/{task_id}", status_code=204)
def delete_task(task_id: int):
    if not service.delete_task(task_id):
        raise HTTPException(status_code=404, detail="Task not found")
    return Response(status_code=204)

Read the create route top to bottom: FastAPI parses JSON into TaskCreate; the service trims and checks the title; the repository assigns the ID and timestamp; TaskRead shapes the response; status 201 says a resource was created. This course uses 422 consistently for invalid input or a failed title rule, 404 for a missing record, and 204 for a successful delete with no body.

The React code from Chapter 07 calls the development proxy at /api/tasks; Vite strips /api before FastAPI receives the request. The server route itself is /tasks. React checks response.ok and uses the returned JSON; it never queries SQLite. The Tauri/Rust versus FastAPI-sidecar choice is covered in Chapter 10.

Wire the modules once, then run the app

There is one FastAPI object. The route module defines an APIRouter; main.py includes it. Keep these files inside a Python package with an empty __init__.py so the relative imports work:

Project shape and Python · app/main.pyapp/
  __init__.py
  main.py
  models.py
  repository.py
  service.py
  routes.py

from fastapi import FastAPI
from .routes import router

app = FastAPI(title="Task API")
app.include_router(router)

From the folder that contains app/, install FastAPI and Uvicorn in a virtual environment, then run python -m uvicorn app.main:app --reload. The in-memory repository is a learning step, not durable storage: restart the process and its records disappear. The next chapter replaces it with a file-backed SQLite repository. If a browser uses direct cross-origin HTTP, configure FastAPI CORS as shown in Chapter 05; the Vite proxy path used here is same-origin during development.

Common mistake → symptom → fix

  • Accepting a plain dictionary everywhere → typos and missing fields reach business code, and the API contract is hard to document → use a Pydantic request model at each JSON boundary.
  • Returning the create model as the response → clients cannot rely on an ID, or private/internal fields accidentally appear → define a response model such as TaskRead.
  • Putting all rules in the route → every endpoint grows long and tests need HTTP setup → move reusable decisions into a service and keep the route focused on HTTP translation.
  • Returning 200 for every outcome → the React client cannot distinguish success from “not found” → use 201 for creation, 204 for a successful delete, 404 for a missing ID, and clear 4xx errors for client mistakes.
  • Assuming validation means security → a well-shaped request still performs an unsafe action → validate shape with Pydantic, then enforce authorization and domain rules in the service.

Beginner exercise: add an archive flag

This is an optional extension, not the shared Task contract. If you add archived, update the create/read models, an explicit update request, repository and database schema, returned JSON, and tests together. The baseline completion endpoint deliberately accepts only {"done": boolean}. The route asks the service first, then turns “no record” into 404.

Recap and next-step bridge ¶

A Pydantic model is an executable description of JSON data. FastAPI uses it before the endpoint runs, while a response model protects the shape sent back. An endpoint should translate HTTP into a service call, a service should enforce application rules, and a repository should isolate storage. CRUD becomes easier to reason about when each route has a clear method, path, input, output, and error contract.

Our repository is deliberately temporary. In Chapter 9, replace its dictionary with SQLite tables and parameterized SQL while keeping the endpoint contract stable. That is the payoff of separation: the screen can continue speaking in tasks even as the storage implementation becomes persistent.
