Chapter 05 · Core skill

Async JavaScript, HTTP, and JSON

A desktop interface often waits for a backend or database. Learn how JavaScript waits for that result without freezing the whole window.

Estimated time: 45–60 minRead, type, explain, practice

Purpose and objectives ¶

A useful desktop screen rarely has all its data at the instant it opens. It may need to ask a local API for tasks, wait for the answer, and then show either a list or a helpful error. This chapter explains that waiting without freezing the interface. You will follow one task from a JavaScript object, across an HTTP request, into a JSON response, and back into the screen.

By the end, you should be able to:

  • Describe a Promise as a future success value or failure, and use async and await to read asynchronous code.
  • Describe the request/response flow: method, URL, headers, body, status, and response body.
  • Encode JavaScript data with JSON.stringify(), decode JSON with response.json() or JSON.parse(), and handle network, HTTP, and data errors separately.

Vocabulary and the waiting mental model ¶

Asynchronous means an operation can finish later, while JavaScript remains able to handle clicks and rendering. A Promise is the envelope for that future result. It starts pending, then becomes fulfilled with a value or rejected with an error. A Promise is not the result itself: it is a way to receive the result when it is ready.

async marks a function as asynchronous. Such a function always returns a Promise, even when it returns an ordinary value. await asks for the value inside a Promise and pauses only the current async function. The browser can continue painting the page and responding to other events.

For comparison, the older style attaches .then() and .catch() to a Promise. async/await uses the same Promise machinery, but lets a sequence of steps look like ordinary top-to-bottom code.

JavaScriptasync function getGreeting() {
  const response = await fetch("/api/tasks");
  return response.status;
}

getGreeting().then((status) => console.log(status));

The call to fetch() returns a Promise immediately. The first await waits for the response headers. The function later returns a status number, wrapped in another Promise. The final line registers what to do when that Promise fulfills; it does not pretend the answer is available synchronously.

HTTP: a conversation in two messages ¶

HTTP is a standard conversation between a client and a server. The client sends a request; the server sends a response. A request has a URL, an HTTP method, headers, and sometimes a body. A response has a status code, headers, and sometimes a body.

  • GET asks to read data, such as /tasks.
  • POST asks the server to create something, usually carrying a body.
  • PATCH changes part of an existing record; DELETE removes one.

Status codes are grouped by their first digit. A 2xx status means success (for example, 200 or 201); 4xx means the request or permission was a client-side problem (such as 400, 401, or 404); and 5xx means the server could not complete a valid request. A status is information from the server, not automatically a JavaScript exception.

Boundary reminder

This lesson demonstrates the FastAPI HTTP path. React sends requests; the trusted API or Tauri command owns validation and storage. The full desktop architecture comparison is in Chapters 01 and 10.

JSON is the shared envelope ¶

JSON (JavaScript Object Notation) is text used to carry objects and arrays between programs. It supports strings, numbers, booleans, null, arrays, and objects. JSON object keys use double quotes, and JSON has no comments or undefined.

JSON.stringify(value) turns a JavaScript value into JSON text for a request body. JSON.parse(text) turns JSON text into a JavaScript value. The response.json() method performs the read-and-parse step for an HTTP response and is itself asynchronous.

JavaScriptconst task = { title: "Prepare report", done: false };
const requestBody = JSON.stringify(task);
// requestBody is the text: {"title":"Prepare report","done":false}

const copy = JSON.parse(requestBody);
console.log(copy.title); // Prepare report

The object is convenient inside JavaScript, while the string is what travels over HTTP. Dates, functions, and custom class instances need deliberate handling; keep this beginner example to plain data records.

Worked example: load and create tasks ¶

During browser development, the frontend calls the same-origin Vite proxy at /api/tasks. Vite forwards this to FastAPI’s /tasks route on 127.0.0.1:8000 (configuration below). Read the function as a pipeline: start request → receive response → verify status → decode body → return usable data.

JavaScriptasync function loadTasks() {
  const response = await fetch("/api/tasks");
  if (!response.ok) {
    throw new Error(`Load failed (${response.status})`);
  }
  const tasks = await response.json();
  return tasks;
}
  1. async function makes loadTasks return a Promise.
  2. fetch sends a default GET request. The first await produces a Response object when the server answers.
  3. response.ok is true for status 200–299. If it is false, the explicit throw turns an HTTP failure into an error your caller can handle.
  4. response.json() reads the response body and parses it. The second await matters because reading the body also takes time.
  5. The returned value is an array of task objects, not raw JSON text.

Now create one task. The method, header, and body tell the API what kind of data it is receiving.

JavaScriptasync function createTask(title) {
  const response = await fetch("/api/tasks", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ title }),
  });
  if (!response.ok) {
    throw new Error(`Save failed (${response.status})`);
  }
  return await response.json();
}

async function demonstrateCreate() {
  const saved = await createTask("Prepare report");
  console.log(saved.id, saved.title, saved.done, saved.created_at);
}

void demonstrateCreate().catch((error) => console.error(error));

The header says the body is JSON, and JSON.stringify supplies the text. This contract sends only { title }; the server assigns the ID, completion flag, and timestamp, then returns the full saved Task with 201 Created. The call runs inside demonstrateCreate, so it works in an ordinary module without relying on top-level await.

Three failure layers, one friendly UI ¶

Put the request in try/catch so the screen can stop showing “Loading…” and show a useful message. A network failure (server stopped, refused connection, or blocked request) may cause fetch to reject and produce no normal response. An HTTP error such as 404 or 500 does produce a response, so catch will not run unless you check response.ok and throw. Finally, malformed JSON can make response.json() reject.

JavaScriptasync function refreshTasks(showTasks, showError) {
  try {
    const tasks = await loadTasks();
    showTasks(tasks);
  } catch (error) {
    console.error(error);
    showError("Tasks could not be loaded. Check the local service and try again.");
  }
}

showTasks and showError are functions supplied by the screen; they are not magic libraries. Keeping the API function responsible for fetching and the UI responsible for messages makes each part easier to test. In a real screen, set loading state before calling, disable a duplicate submit while saving, and clear or replace loading state in both success and failure paths.

Local development and CORS

A scheme, host, and port form an origin. The Vite proxy below makes the browser call its own origin, so CORS is not needed for that development request. If you call FastAPI directly from a different origin, the API must explicitly allow that origin. CORS is not authentication; a packaged sidecar still needs loopback binding, controlled startup, and a deliberate security boundary.

Route one development URL to FastAPI

Keep the frontend call simple: fetch("/api/tasks"). Add this server.proxy entry to your existing Vite configuration; keep any React plugin already present. The development server strips the prefix and forwards the request, so FastAPI receives /tasks, /tasks/7, and the other routes described in Chapter 01.

JavaScript · vite.config.js (merge this server section)import { defineConfig } from "vite";

export default defineConfig({
  server: {
    proxy: {
      "/api": {
        target: "http://127.0.0.1:8000",
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ""),
      },
    },
  },
});

The proxy exists only while Vite’s development server is running. It is not bundled into a production Tauri app. A packaged app must deliberately choose a Tauri/Rust command or a FastAPI sidecar with a configured URL, lifecycle, permissions, and origin policy; do not assume /api will work by magic once the proxy is gone.

If you choose a direct cross-origin dev request instead

Allow only the actual frontend origins you use, not every website. This example has no cookie authentication, so credentials stay disabled:

Python · FastAPI CORS middlewarefrom fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "http://localhost:5173",
        "http://127.0.0.1:5173",
    ],
    allow_credentials=False,
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Content-Type"],
)

Keep the route at /tasks if calling FastAPI directly. The browser URL, scheme, host, and port must match one of the allowed origins exactly. A packaged Tauri webview uses a different origin; determine and configure it deliberately rather than copying these development values.

Official references: Vite server proxy options · FastAPI CORS guide.

Common mistake → symptom → fix

  • Forgetting await: the UI receives a Promise and tasks.map fails. Fix: await the Promise inside an async function.
  • Assuming 500 enters catch: the code tries to parse an error page as a successful list. Fix: check response.ok before reading the body.
  • Sending an object as body: the server reports invalid JSON. Fix: use JSON.stringify and the Content-Type header.
  • Calling response.json() twice: the second read fails because a response body is consumed. Fix: parse once and reuse the resulting value.
  • Using the wrong URL or assuming FastAPI is present: the request is refused. Fix: start the separate sidecar, verify its route, and keep its lifecycle explicit.

Beginner exercise

Write loadOneTask(id) for GET /api/tasks/7. It should check response.ok, throw an error containing the status when needed, parse JSON, and return the task. Then state what differs between a refused connection and a 404.

Show the worked answer and explanation 
JavaScriptasync function loadOneTask(id) {
  try {
    const response = await fetch(`/api/tasks/${id}`);
    if (!response.ok) {
      throw new Error(`Task lookup failed (${response.status})`);
    }
    return await response.json();
  } catch (error) {
    console.error("Could not load task", error);
    throw error;
  }
}

The template string places the ID in the URL. The first await gets a response, ok distinguishes 2xx from HTTP errors, and the second await decodes the body. A refused connection generally means no response was created, so fetch rejects. A 404 is a response from a reachable server saying that this task or route was not found; the explicit check turns it into the same catchable error shape for the caller.

Recap and next-step bridge ¶

A Promise represents a future result; async/await makes its steps readable without blocking the whole UI. HTTP carries a request and response across a boundary. JSON is text on that boundary, converted with JSON.stringify going out and response.json() or JSON.parse coming in. Check status explicitly, catch network and parsing failures, and give the user a loading, success, or error state.
