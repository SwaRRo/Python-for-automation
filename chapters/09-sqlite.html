Chapter 09 · Data foundation

SQL and SQLite: persistent records

A database stores structured facts beyond the lifetime of one process. Learn relational tables, keys, CRUD queries, and how to preserve history instead of overwriting it.

Estimated time: 50–70 minRead, type, explain, practice

Purpose: make records outlive the process

In Chapter 08, a FastAPI endpoint could validate a request and return JSON. That data still disappears if the process stops unless we store it. SQLite gives a small app a durable, relational file: rows remain after a restart, and SQL lets us ask precise questions about them.

By the end, you can…

  • Model related app data with tables, primary keys, and foreign keys.
  • Use SELECT, INSERT, UPDATE, DELETE, and a join.
  • Keep user values parameterized, group dependent writes in a transaction, and evolve a schema safely.
  • Explain which layer owns database access in a React + FastAPI + Tauri app.

Vocabulary and the relational mental model

Think of a database as several carefully labeled spreadsheets, plus rules that keep them consistent. A table stores one kind of entity; a row is one entity; a column is one attribute; and a schema is the database’s structure and constraints.

Primary key
A value that uniquely identifies a row. An integer id is a common choice.
Foreign key
A column whose value must refer to a key in another table. It expresses a relationship.
CRUD
Create, Read, Update, Delete: the four everyday data operations.
Join
A query that combines related rows, usually by matching a primary key to a foreign key.
Transaction
A group of changes treated as one unit: commit all of them, or roll them all back.
Migration
A deliberate, repeatable schema change, such as adding a column to an existing database.

Good relational modeling stores a fact once and connects to it. For our task list, tasks owns the task title and status. task_events owns a history of actions. Repeating the title in every event would create stale copies when the title changes.

Worked example: tasks and their event history

Start with tables that state the rules. NOT NULL means a value is required. DEFAULT supplies a value when the application omits it. REFERENCES tasks(id) says that an event cannot point at a task that does not exist.

SQL · schema.sqlPRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS tasks (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 120),
  done INTEGER NOT NULL DEFAULT 0 CHECK (done IN (0, 1)),
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS task_events (
  id INTEGER PRIMARY KEY,
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  event_type TEXT NOT NULL,
  happened_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

The pragma enables foreign-key checks for this SQLite connection; enable it whenever you open the database. SQLite represents a Boolean simply as integer values, so done uses 0 for false and 1 for true. The event table has its own key because each event is a distinct record, while task_id is the link back to its parent task.

Create and read

SQL · CRUDINSERT INTO tasks (title, done, created_at) VALUES (?, ?, ?);

SELECT id, title, done
FROM tasks
WHERE done = 0
ORDER BY created_at DESC;

INSERT INTO task_events (task_id, event_type)
VALUES (1, 'created');

The INSERT names the supplied columns; SQLite generates the ID and supplies the done default if that column is omitted. The backend explicitly assigns created_at as a UTC timestamp, as shown in the Python helper below. The SELECT returns only unfinished tasks and sorts newest first. The second insert records what happened without overwriting the task itself. In real code, do not assume the new task is always id 1; use the ID returned by the insert.

Update, delete, and join

SQL · update, delete, joinUPDATE tasks
SET done = 1
WHERE id = 1;

DELETE FROM task_events
WHERE task_id = 1;

SELECT tasks.title, task_events.event_type, task_events.happened_at
FROM tasks
JOIN task_events ON task_events.task_id = tasks.id
WHERE tasks.id = 1
ORDER BY task_events.happened_at;

The WHERE clause limits the update or delete to one task or its events. The join starts with a task row, matches its id to the event’s task_id, and returns a readable history. A join does not copy data into a new table; it combines matching rows for this result only.

Parameters and transactions in Python

Chapter 08’s FastAPI route is a natural place to call a repository function. The browser sends JSON to FastAPI; Python validates it and talks to SQLite. React does not open the SQLite file directly.

Python · repository writeimport sqlite3
from contextlib import closing
from datetime import datetime, timezone

def add_task(db_path: str, title: str) -> int:
    clean_title = title.strip()
    if not clean_title or len(clean_title) > 120:
        raise ValueError("title must contain 1–120 non-space characters")
    created_at = datetime.now(timezone.utc).isoformat(timespec="seconds").replace("+00:00", "Z")

    with closing(sqlite3.connect(db_path)) as connection:
        connection.execute("PRAGMA foreign_keys = ON")
        with connection:  # commits on success; rolls back on an exception
            cursor = connection.execute(
                "INSERT INTO tasks (title, done, created_at) VALUES (?, ?, ?)",
                (clean_title, 0, created_at),
            )
            task_id = cursor.lastrowid
            connection.execute(
                "INSERT INTO task_events (task_id, event_type) VALUES (?, ?)",
                (task_id, "created"),
            )
    # closing(...) closes the connection; with connection handled the transaction.
    return task_id

closing(...) guarantees that the connection closes. The nested with connection: manages only the transaction: it commits on success and rolls back on an exception. The question marks are placeholders; the tuple supplies values separately, so a title containing quotes is still data rather than executable SQL. lastrowid captures the id SQLite assigned.

The two inserts share one connection and one transaction. If the event insert fails, leaving the block raises an error and the context manager rolls back the pending work. If the block completes, it commits. This prevents a half-created task. For a read, use connection.execute with parameters in the same way, then fetch rows. Never build SQL by concatenating a form value into the query.

Choose the boundary deliberately

One valid learning architecture is React → FastAPI sidecar → SQLite. The Python process owns validation and database access, but its startup, shutdown, loopback-only binding, permissions, and packaging must be designed; exposing a local API more widely than necessary increases the security surface. Another valid desktop architecture is React → Tauri command → Rust SQLite code, avoiding a Python process but requiring carefully scoped Tauri capabilities and Rust-side validation. Tauri does not automatically host FastAPI, and neither option makes direct React-to-SQLite access safe or available by magic.

Persistence and schema change

Pass an explicit database path into the repository. A relative tasks.db path can silently create a different file when the working directory changes. During local web development you can set APP_DATA_DIR=./dev-data; a packaged FastAPI sidecar should receive the platform-specific user-data directory from its Tauri host. A direct Rust implementation should resolve the equivalent directory through Tauri’s path API.

A schema is code too. If version 1 has title and version 2 needs a due date, add a migration rather than silently assuming every old file is empty:

SQL · migration ideaALTER TABLE tasks ADD COLUMN due_date TEXT;

Run this once, record that it ran (for example, with a schema-version table), and test it against a copy of a real older database. Adding a nullable column is a friendly first migration. More complex changes—such as splitting a column or changing a constraint—usually require creating a new table, copying and checking data, renaming tables, and doing the work in a transaction. Back up before migrations; “it worked on a fresh database” is not proof that it works on existing data.

Common mistake → symptom → fix

Missing WHERE

Symptom: every task becomes done, or every row disappears. Fix: write the intended SELECT first with the same condition, inspect the matching ids, then run the update/delete inside a tested function. Require an id argument rather than accepting a vague command.

String-building a query

Symptom: names containing apostrophes break the query, or untrusted input changes what it does. Fix: keep SQL text fixed and pass values through ? placeholders.

Foreign keys assumed but not enabled

Symptom: orphan events appear even though the table says REFERENCES. Fix: execute PRAGMA foreign_keys = ON on every connection and test an invalid task_id deliberately.

Using an in-memory or wrong relative path

Symptom: records “disappear” after restart or differ between launch locations. Fix: use a deliberate absolute application-data path and log which database file is open during development.

Beginner exercise

Write a query that lists unfinished task titles with their event types. Then sketch a Python function that marks task id 7 done and records a completed event as one transaction. What should happen if the event insert fails?

Show the worked answer and explanation 
SQL · answerSELECT tasks.title, task_events.event_type
FROM tasks
JOIN task_events ON task_events.task_id = tasks.id
WHERE tasks.done = 0
ORDER BY tasks.id;

The join connects the two tables, and WHERE tasks.done = 0 filters the parent rows. A Python solution would open one connection, run UPDATE tasks SET done = 1 WHERE id = ? with (7,), then run INSERT INTO task_events (task_id, event_type) VALUES (?, ?) with (7, "completed") inside the same with block. If the second statement fails, the first change rolls back, so the task is not falsely marked complete without its history.

Recap and next-step bridge

Tables model entities, primary keys identify rows, and foreign keys express valid relationships. CRUD changes data; joins read related data together. Parameters protect values and handle punctuation safely. Transactions keep related writes all-or-nothing. A file-backed SQLite database persists across process restarts, while migrations let the schema evolve without discarding existing records.
