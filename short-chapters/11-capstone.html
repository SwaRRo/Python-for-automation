Chapter 11 · Build-along

Capstone: build one complete feature

Bring the concepts together in a small task tracker. You can later swap the data domain for products, stock movements, bookings, or another business workflow.

Estimated time: 1–3 practice sessionsRead, type, explain, practice
Concise version. This preserves the earlier, shorter lesson. Open the expanded Chapter 11 lesson for the full walkthrough.

By the end, you can…

  • Write pseudocode and agree on the record/API contract before generating code.
  • Connect one UI action through validation to durable storage.
  • Audit generated code and test success and failure paths.

1. Specify the small vertical slice ¶

A vertical slice is one user-visible feature implemented across the layers. Keep the scope small: list tasks, create a task, mark one complete, and retain changes after restart.

Record:
  id: unique integer
  title: non-empty text
  done: boolean
  created_at: timestamp

On screen load:
  show loading state
  request saved tasks
  show list or a useful error

On submit:
  reject blank title in the UI for convenience
  send the new title to the trusted backend
  backend validates and stores it
  return saved task with its generated ID
  add/update it in UI state

On completion:
  request a state change
  save it
  show the returned saved value

For a different domain, change the record, invariants, and transitions. Example: a product has a code/name; stock movements are separate records with a quantity and reason. Never silently let an invalid movement make inventory negative if that violates the real business rule.

2. Build in small working checkpoints ¶

  1. Build the static HTML form and list with example data.
  2. Convert the UI into React components and props.
  3. Put the editable list in state; add controlled inputs and event handlers.
  4. Create FastAPI request and response models and an in-memory endpoint.
  5. Connect one frontend fetch call; handle loading, HTTP failure, and network failure.
  6. Replace in-memory storage with SQLite and parameterized queries.
  7. Choose the Tauri integration path and package a development build only after the feature works.
  8. Restart the app and prove the saved record persists.

If following a direct-Rust architecture, replace the API call with a narrow Tauri command and have Rust perform the database operation. Keep the same contract and tests where possible.

3. Use AI as a pair, not as an oracle ¶

Ask for one bounded file or behavior at a time. For example:

“I’m learning. Generate a React component for a task list. It receives tasks and onToggle as props, uses task.id as key, displays a status, and does not fetch data or add styling libraries. Explain every part and name assumptions.”

Then ask for one FastAPI endpoint that matches a written request/response example. Ask the model to compare frontend fields with the API model. Avoid asking it to build an entire ERP in one prompt.

Audit the result by following the data: source → type/shape → validation → state update → database write → response/error. Ask what happens when the user double-clicks, the server is offline, the title is empty, the record ID does not exist, and the app restarts.

4. Test behavior, not just appearance ¶

Try a successful create, an empty title, a duplicate submission, a server-offline case, a missing record, and a restart. If using a task tracker, verify completed status is still correct after reload. If using inventory, test the quantity limits and movement history. Check the database as well as the UI.

Use Git commits after each small working milestone. Keep the project runnable. Record how to start the frontend, backend, and desktop wrapper; document known limitations. For a release, investigate signing, installers, updates, database backup/migration, and how your chosen backend is bundled.

Your “done” definition

A feature is not finished just because the button looks right. It should reject invalid input, report failures honestly, save the intended value, survive restart when persistence is promised, and be understandable enough that you can trace its data flow.

Practice it

Write a one-page pseudocode spec for one feature you genuinely want to build. Include fields, validation rules, who can change the data, success behavior, and at least three failure cases. Then implement the smallest end-to-end version you can run locally.

Show answer guidance

A strong spec uses concrete fields and transitions rather than “manage everything.” Example: a note has title/body/archived; title is required; create returns an ID; archive changes a boolean; missing IDs return 404; database failures show a retryable message. If the app is for multiple people, specify how identity and shared storage work before calling it a desktop-only problem.
