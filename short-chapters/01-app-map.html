Chapter 01 · Start here

Map the app before writing code

Learn the moving parts of a desktop application and trace a single piece of data through the interface, backend, and storage. This map will make every later chapter easier to place.

Estimated time: 25–40 minRead, type, explain, practice
Concise version. This preserves the earlier, shorter lesson. Open the expanded Chapter 01 lesson for the full walkthrough.

By the end, you can…

  • Name the jobs of HTML, CSS, JavaScript, React, Python, FastAPI, SQLite, Rust, and Tauri.
  • Trace a record from a form into storage and back to a list.
  • Understand that Tauri does not automatically run a Python API.

The four layers ¶

A useful application has a presentation layer (what the user sees), application logic (rules and actions), data access (reading and writing), and persistence (where data remains after closing). The names of the technologies are less important than knowing which job each one performs.

  • HTML gives content structure; CSS controls presentation; JavaScript makes the interface interactive.
  • React is a JavaScript library for composing UI pieces and keeping the screen in sync with data.
  • Python can implement backend rules; FastAPI exposes those rules as HTTP endpoints.
  • SQLite stores relational data in a database file.
  • Tauri wraps a web frontend in a desktop application. Its host-side logic is written in Rust.

These parts are choices, not a mandatory pile. A small Tauri app can call Rust commands directly and use SQLite from the Rust side. If you keep FastAPI, it is a separate local service or sidecar process that you must package and manage.

Follow one request ¶

Suppose a user adds a task called “Prepare monthly report.” The form stores its current text in the UI. When the user saves, the frontend sends a request with that text. The backend checks it, writes a row into a database, and responds with the saved task including its ID. The UI updates its list from that response.

Person types → form state → save action → API or Tauri command
    → validation → database write → response → updated list

Each arrow is a boundary where data changes shape or an error may occur. Learning to trace those arrows is more valuable than memorizing a framework’s vocabulary.

Why can’t React just write to SQLite?

React runs in a webview and should not receive unrestricted access to the user’s files. A trusted boundary—Rust/Tauri commands or a local API—performs privileged work and validates requests.

Tools and a calm workflow ¶

For practice, install a code editor, Git, Node.js, and Python. When you reach Tauri, follow its current operating-system prerequisites and install Rust using the official Rust toolchain. You can learn most JavaScript concepts in a browser console before creating a project.

Work in layers: make a static page, add JavaScript, then React state, then a backend request, then database persistence. At each step, keep the previous layer working. This makes failures small enough to understand.

Use a tiny data contract, such as {"id": 7, "title": "Prepare monthly report", "done": false}. Agree on field names and types before writing the frontend and backend independently.

Practice it

Draw four boxes for UI, application rules, data access, and storage. Draw arrows for loading a list and saving a new record. Label which language or tool owns each box in the architecture you currently imagine.

Show answer guidance

One reasonable diagram is React in the Tauri webview → a Rust command or FastAPI endpoint → validation/business logic → SQLite. If FastAPI is used, add a separate-process box and explicitly plan how Tauri starts and stops it.
