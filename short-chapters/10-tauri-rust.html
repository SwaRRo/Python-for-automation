Chapter 10 · Desktop integration

Tauri, Rust, and the desktop boundary

Tauri turns a web frontend into a desktop application. Learn the boundary between the webview and native host, plus enough Rust vocabulary to read a command.

Estimated time: 50–75 minRead, type, explain, practice
Concise version. This preserves the earlier, shorter lesson. Open the expanded Chapter 10 lesson for the full walkthrough.

By the end, you can…

  • Describe Tauri’s frontend, Rust host, and capability/permission boundary.
  • Read a small Rust command and understand its JavaScript caller.
  • Choose deliberately between a Rust-backed local API and a Python sidecar.

What Tauri adds ¶

A Tauri app typically has a web frontend rendered in a system webview and a Rust process that owns native desktop capabilities. The frontend is not automatically granted arbitrary filesystem or shell access. Tauri v2 uses capabilities and permissions to control which windows can call which plugin/commands.

A command is a Rust function deliberately exposed to the frontend. For example:

#[tauri::command]
fn greet(name: &str) -> String {
    format!("Hello, {name}!")
}

Frontend code can call it using Tauri’s JavaScript API:

import { invoke } from "@tauri-apps/api/core";

const greeting = await invoke("greet", { name: "Ada" });

The argument names must match the command’s expected inputs. The result is delivered asynchronously to JavaScript as a Promise.

Just enough Rust to read a command ¶

Rust has explicit types. fn starts a function declaration; -> String describes the return type. &str is a borrowed string slice, and format! constructs a new String. You will encounter structs for records, enums for a value with several named variants, and Result<T, E> for operations that can succeed or fail.

You do not need to become a Rust expert before using Tauri. Learn function signatures, structs, enums, ownership/borrowing at a conceptual level, error handling with Result, and how to read compiler messages. Use the Rust Book when you are ready to go deeper.

Choose the backend arrangement intentionally ¶

Option A: Tauri/Rust owns local data access. The UI invokes Rust commands; Rust applies rules and uses an appropriate SQLite library/plugin. This can make a self-contained desktop deployment simpler because there is no separate HTTP service to start. You still need schema migrations, validation, error handling, and carefully scoped permissions.

Option B: keep FastAPI as a sidecar. The UI calls a Python API over loopback, and FastAPI manages data. This can reuse Python skills or an existing service, but packaging is more involved: bundle the Python environment/executable, start and stop it with the desktop app, choose a safe loopback port or another IPC mechanism, handle failures, and avoid exposing an unauthenticated API to the local network.

For a multi-user remote ERP, an API may live on a real server and the desktop app becomes a client. That is a different deployment topology from a single-user offline desktop app. Pick the architecture based on who shares data, whether offline use matters, and how updates/backups will work.

Permissions are not a TODO

Do not grant broad shell or filesystem capabilities just to make a prototype work. Expose narrow commands such as “save note” rather than arbitrary SQL or arbitrary file access, validate at the trusted boundary, and follow the Tauri v2 security guide.

Practice it

Choose an architecture for each case: (1) an offline personal notes desktop app; (2) a business system used by a whole team from multiple computers; (3) an existing Python service with complex rules. State where data lives and which process validates writes.

Show answer guidance

There is no universal answer. (1) often fits local SQLite accessed through a narrow Rust command; (2) usually needs a shared server database and authenticated API; (3) may keep FastAPI as a service/sidecar, but its lifecycle and access controls must be designed. The point is to articulate tradeoffs before generating code.
