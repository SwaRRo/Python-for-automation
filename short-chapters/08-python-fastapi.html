Python refresh and FastAPI endpoints

You already know some Python. Reuse that knowledge to build a small HTTP API: functions receive validated input, apply rules, call data-access code, and return a response.

Estimated time: 50–70 minRead, type, explain, practice
Concise version. This preserves the earlier, shorter lesson. Open the expanded Chapter 08 lesson for the full walkthrough.

By the end, you can…

  • Recognize Python types, functions, dictionaries, and lists in API code.
  • Define FastAPI request/response models and CRUD endpoints.
  • Handle validation and errors at the server boundary.

Python objects and type hints ¶

Python dictionaries and lists map naturally to JSON objects and arrays. Type hints make intended inputs and outputs clearer, though they do not replace runtime validation on their own.

from pydantic import BaseModel

class TaskCreate(BaseModel):
    title: str
    done: bool = False

class TaskRead(TaskCreate):
    id: int

FastAPI uses Pydantic models to parse and validate request data. A request with the wrong type or missing required title receives a validation response rather than being silently accepted.

An endpoint is a function reached by an HTTP request ¶

A route combines an HTTP method and path. A simple in-memory example illustrates the contract; a real app replaces the dictionary with a database repository.

from fastapi import FastAPI, HTTPException

app = FastAPI()
tasks: dict[int, dict] = {}
next_id = 1

@app.get("/tasks", response_model=list[TaskRead])
def list_tasks():
    return list(tasks.values())

@app.post("/tasks", response_model=TaskRead, status_code=201)
def create_task(item: TaskCreate):
    global next_id
    saved = {"id": next_id, **item.model_dump()}
    tasks[next_id] = saved
    next_id += 1
    return saved

This is only a teaching sketch; in-memory data disappears when the process restarts. Real CRUD also needs read-by-ID, update, and delete operations, explicit data-access code, and tests.

Validation, errors, and frontend agreement ¶

Define what each endpoint accepts and returns. For example: POST /tasks accepts a title and optional done flag, then returns a saved task with an ID. Return appropriate status codes: 201 for creation, 404 when a record does not exist, and 422 for invalid input (FastAPI handles model validation). Avoid returning raw stack traces to the user.

Keep business rules on the server too. A browser can be modified; never trust the UI alone to enforce rules. Put CORS middleware in development only for the origins that need access. In production, configure the allowed origin intentionally.

From Python route to SQLite

Keep endpoint functions understandable: parse/validate request → call a service/repository → return a response model. Avoid mixing UI concerns into the database layer. Chapter 9 introduces SQL and persistence.

Practice it

Write a Pydantic model for a note with title and optional archived status. Sketch GET /notes and POST /notes as Python functions. State which response fields should be generated by the server rather than trusted from the client.

Show answer guidance

The client supplies the title and perhaps archived status. The server/database should assign the unique ID and may set created_at. A response model can expose those saved fields. For production CRUD, persist through a repository instead of the chapter’s in-memory dictionary.
