Chapter 09 · Data foundation

SQL and SQLite: persistent records

A database stores structured facts beyond the lifetime of one process. Learn relational tables, keys, CRUD queries, and how to preserve history instead of overwriting it.

Estimated time: 50–70 minRead, type, explain, practice
Concise version. This preserves the earlier, shorter lesson. Open the expanded Chapter 09 lesson for the full walkthrough.

By the end, you can…

  • Explain tables, rows, columns, primary keys, and foreign keys.
  • Write basic SELECT, INSERT, UPDATE, and DELETE statements.
  • Use parameterized queries and transactions from application code.

Model entities and relationships ¶

A table represents one type of thing; each row is one record and each column is a field. A primary key uniquely identifies a row. A foreign key connects a row to another table. Relational design avoids storing the same changing fact in many places.

CREATE TABLE tasks (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  done INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE task_events (
  id INTEGER PRIMARY KEY,
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  event_type TEXT NOT NULL,
  happened_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

The second table records events connected to a task. It is often better to preserve a history record than overwrite information when auditability matters.

The four CRUD operations ¶

SQL names the operation and the table. Use an explicit column list for inserts.

-- Read
SELECT id, title, done FROM tasks ORDER BY id DESC;

-- Create
INSERT INTO tasks (title) VALUES ('Prepare report');

-- Update
UPDATE tasks SET done = 1 WHERE id = 7;

-- Delete
DELETE FROM tasks WHERE id = 7;

Always check that an update/delete has a suitable condition. Without WHERE, you may change every row. SQLite is embedded and stores data in a file, but concurrent access, migrations, backups, and app lifecycle still deserve thought.

Pass data safely and group related writes ¶

Do not build SQL by joining untrusted text into a string. Use parameterized statements so the database treats values as data.

cursor.execute(
    "INSERT INTO tasks (title) VALUES (?)",
    (title,)
)

Use a transaction when several writes must succeed or fail together. For example, create a task and insert its first history event in one transaction. Otherwise you could end with a task that has no matching event.

Enable foreign-key enforcement where your SQLite connection requires it, create schema migrations as the application evolves, and decide where the database file lives. A packaged Tauri app should use the app’s data directory, not assume its current working directory is writable.

Useful mental model: a database is durable shared state for your application, not a magic file that automatically validates every business rule.

Practice it

Design a tiny notes database with notes and note_tags. Identify each primary key and foreign key. Write a SELECT query that lists a note’s title and its tags. Then write a parameterized INSERT example in the language you plan to use.

Show answer guidance

A note_tags table can contain note_id and tag_id as foreign keys; a composite uniqueness rule can prevent duplicate links. For a learning project, start with one table and a primary key before modeling many-to-many relationships. The important habit is to keep parameter values separate from SQL text.
